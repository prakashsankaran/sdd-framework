1. Purpose

This Database Design Document serves as the authoritative blueprint for the Project Nexus persistence layer. The core objectives of Project Nexus are to resolve a critical 25% drop in consumer retention, optimize database performance for ultra-fast, mobile-optimized load times, and empower users through an advanced, self-service billing system.

By implementing this highly optimized relational schema, Project Nexus aims to deflect customer service workloads and achieve a 40% reduction in support call volume within six months of deployment. This document defines the structural representation, rules, relationships, security schemas, performance profiles, and archival pathways supporting these strategic initiatives.

2. Database Overview

The chosen architecture for Project Nexus relies on a highly scalable, clustered relational database system designed to maintain strict consistency for financial transactions while delivering low-latency reads for mobile and web frontends.

Attribute Specification
Database Engine PostgreSQL Engine (AWS Aurora Serverless v2 Multi-AZ Deployment)
Version Compatibility PostgreSQL Version 16.2
Primary Architectural Purpose To serve as the primary System of Record (SoR) for user portal profiles, payment profiles, statements, and transaction processing. It achieves sub-50ms API read times to prevent abandonment, directly addressing retention issues.
Hosting Architecture Highly-Available (HA) Aurora cluster with 1 primary writer instance and 2 auto-scaling read-replicas distributed across multiple availability zones.

8. Views

For secure abstraction and reporting efficiency, view layers aggregate operational billing metrics and customer performance insights.

8.1 View Name: vw_customer_retention_risk

Purpose: Identifies at-risk customers by isolating profiles without active logins in over 30 days combined with delinquent account configurations.

CREATE OR REPLACE VIEW vw_customer_retention_risk AS SELECT u.user_id, u.full_name, u.email, u.last_login_at, ba.account_id, ba.account_status, ba.current_balance, EXTRACT(DAY FROM (CURRENT_TIMESTAMP - u.last_login_at)) AS days_inactive FROM users u JOIN billing_accounts ba ON u.user_id = ba.user_id WHERE u.last_login_at < CURRENT_TIMESTAMP - INTERVAL '30 days' OR ba.account_status = 'DELINQUENT';

8.2 View Name: vw_billing_performance_metrics

Purpose: Used by analytical dashboard modules to audit processing success levels across payment vectors without exposing customer details.

CREATE OR REPLACE VIEW vw_billing_performance_metrics AS SELECT payment_method_type, status AS transaction_status, COUNT(transaction_id) AS volume_count, SUM(amount) AS total_processed_volume, COUNT(CASE WHEN status = 'FAILED' OR status = 'DECLINED' THEN 1 END) AS error_count, ROUND((COUNT(CASE WHEN status = 'SUCCESS' THEN 1 END)::NUMERIC / COUNT(*)::NUMERIC) * 100, 2) AS payment_success_rate FROM transactions_log tx LEFT JOIN payment_profiles pp ON tx.payment_profile_id = pp.payment_profile_id GROUP BY payment_method_type, status;

9. Stored Procedures

Encapsulated logic layers manage sensitive operational sequences to maintain ledger safety and guarantee concurrency handling.

9.1 Procedure Name: sp_execute_self_service_payment

Purpose: Fully atomic safe execution script that coordinates payments against outstanding customer statements, balancing ledger logs and invoice registers.

CREATE OR REPLACE PROCEDURE sp_execute_self_service_payment( p_account_id UUID, p_invoice_id UUID, p_payment_profile_id UUID, p_payment_amount NUMERIC(12,2), p_gateway_ref VARCHAR(128), OUT r_transaction_id UUID, OUT r_success BOOLEAN ) LANGUAGE plpgsql AS $$ DECLARE v_current_due NUMERIC(12,2); v_tx_id UUID; BEGIN -- Initialize variables r_success := FALSE; v_tx_id := gen_random_uuid(); -- Check invoice balance SELECT (amount_due - amount_paid) INTO v_current_due FROM invoices WHERE invoice_id = p_invoice_id AND account_id = p_account_id FOR UPDATE; IF NOT FOUND THEN RAISE EXCEPTION 'Target invoice record not identified.'; END IF; IF p_payment_amount <= 0.00 THEN RAISE EXCEPTION 'Payment parameter must evaluate positive.'; END IF; -- Create Ledger Transaction entry INSERT INTO transactions_log ( transaction_id, account_id, invoice_id, payment_profile_id, amount, transaction_type, status, gateway_reference, created_at ) VALUES ( v_tx_id, p_account_id, p_invoice_id, p_payment_profile_id, p_payment_amount, 'CHARGE', 'SUCCESS', p_gateway_ref, CURRENT_TIMESTAMP ); -- Adjust invoice registers UPDATE invoices SET amount_paid = amount_paid + p_payment_amount, status = CASE WHEN (amount_paid + p_payment_amount) >= amount_due THEN 'PAID' ELSE 'PARTIALLY_PAID' END WHERE invoice_id = p_invoice_id; -- Adjust Customer Balance profile UPDATE billing_accounts SET current_balance = current_balance - p_payment_amount, updated_at = CURRENT_TIMESTAMP WHERE account_id = p_account_id; r_transaction_id := v_tx_id; r_success := TRUE; EXCEPTION WHEN OTHERS THEN -- Rollback logic automatically executed by postgres engine r_success := FALSE; RAISE; END; $$;

10. Triggers

Automated database behaviors prevent bad states from leaking into the system and handle real-time calculation tasks.

10.1 Trigger Name: trg_sync_account_delinquency

Event: AFTER UPDATE on billing_accounts

Purpose: Tracks status adjustments to trigger real-time communications to customers, preventing customer churn and keeping user accounts active.

CREATE OR REPLACE FUNCTION fn_evaluate_delinquency() RETURNS TRIGGER AS $$ BEGIN IF NEW.current_balance > 100.00 AND NEW.account_status = 'ACTIVE' THEN -- Set account status to delinquent UPDATE billing_accounts SET account_status = 'DELINQUENT', updated_at = CURRENT_TIMESTAMP WHERE account_id = NEW.account_id; END IF; RETURN NEW; END; $$ LANGUAGE plpgsql; CREATE TRIGGER trg_sync_account_delinquency AFTER UPDATE OF current_balance ON billing_accounts FOR EACH ROW EXECUTE FUNCTION fn_evaluate_delinquency();

11. Sequences & Identity Columns

To ensure horizontal scaling across nodes and low-latency client creation cycles, standard continuous integer sequences are excluded from primary key designs.

  • UUID Key Strategy: All physical records across users, billing_accounts, payment_profiles, and invoices leverage random UUID generators (UUIDv4) via the native gen_random_uuid() engine component.
  • Invoice Number Sequence: A localized sequence handles the creation of chronological invoice numbers for customer communication.
CREATE SEQUENCE seq_invoice_numbers START WITH 100001 INCREMENT BY 1 NO MAXVALUE CACHE 10;

13. Normalization

The core schema has been structured to meet standard normalization models while applying strategic modifications to ensure high performance.

  • First Normal Form (1NF): Enforced. All table cells contain single atomic attributes, and unique identifier mechanisms govern every operational table.
  • Second Normal Form (2NF): Enforced. No partial-key functional dependencies exist across the persistence landscape. Non-prime fields map directly to their full primary structures.
  • Third Normal Form (3NF): Enforced. No transitive dependencies are present. Field updates remain isolated, preventing updates from cascading across unrelated tables.
  • Deliberate Denormalization Strategy: The table transactions_log deviates from third normal form by storing a JSONB object: gateway_response_payload. Storing this unstructured data in JSONB prevents database locking delays and avoids complex child tables, ensuring fast transaction logging during peak checkout activity.

14. Security

Protecting customer financial data and portal identity values is core to the database design of Project Nexus.

14.1 Encryption at Rest & Transit

All tables are encrypted at rest using industry-standard AES-256 keys, managed automatically via AWS Key Management Service (KMS). In-transit connections enforce TLS 1.3 protocol requirements, rejecting unencrypted HTTP/TCP requests.

14.2 Data Masking & PCI-DSS Compliance

Raw credit card primary account numbers (PAN) or security codes (CVV) are never saved to our database. Payment data is securely sent to third-party processors, which return reference tokens saved in payment_profiles.gateway_token. Secondary identifiers utilize irreversible masking patterns (e.g. payment_profiles.masked_identifier displays only trailing digits: ************4242).

14.3 PII and GDPR Compliance

Table Name PII Column Classification Class GDPR / Right to Erasure Masking Protocol
users email High Sensitivity Anonymized during profile termination via hash processing (e.g., anon_user_872@nexus.internal).
users full_name Medium Sensitivity Replaced with generic identifier ("Active Citizen Profile").

16. Performance Optimization

This section details the performance design built directly into the database engine to maintain fast, responsive connections across both mobile and desktop platforms.

16.1 Table Partitioning (transactions_log)

Because the transactions_log table processes high-volume writes, it is partitioned by month based on the created_at timestamp. This prevents index bloat and ensures queries only scan relevant monthly partitions instead of the entire dataset.

-- Partitioning transaction log definitions CREATE TABLE transactions_log ( transaction_id UUID NOT NULL, account_id UUID NOT NULL, invoice_id UUID, payment_profile_id UUID, amount NUMERIC(12,2) NOT NULL, transaction_type VARCHAR(32) NOT NULL, status VARCHAR(32) NOT NULL, gateway_reference VARCHAR(128), gateway_response_payload JSONB, error_code VARCHAR(64), created_at TIMESTAMPTZ NOT NULL, client_ip INET, PRIMARY KEY (transaction_id, created_at) ) PARTITION BY RANGE (created_at); -- Sample Partition creation CREATE TABLE transactions_log_y2024_m04 PARTITION OF transactions_log FOR VALUES FROM ('2024-04-01 00:00:00+00') TO ('2024-05-01 00:00:00+00');

16.2 Database Statistics Updates

To ensure our query planner chooses the most efficient execution paths, the database relies on automatic engine analysis combined with targeted maintenance window optimizations:

  • Autovacuum is configured to target highly modified tables (such as transactions_log) when more than 10% of their records change.
  • An optimized maintenance job runs weekly on Sunday at 02:00 UTC, triggering a full ANALYZE run to update system statistics and prevent slow queries.

18. Migration Strategy

This section outlines the steps to safely migrate production traffic from our legacy system to the modernized Project Nexus infrastructure with minimal downtime.

18.1 Schema Versioning & Deployments

All database structure changes are written in SQL and managed using Liquibase. Every change is tracked as a version-controlled migration script, and these scripts are applied automatically during deployment pipeline updates.

18.2 Zero-Downtime Blue-Green Cutover Pattern

To protect our systems during deployment, we use a Blue-Green deployment pattern to cut over active web and mobile traffic:

  1. Database Replication: We set up a new production database instance (Green) running the updated Project Nexus schema, and replicate data from the active production database (Blue) in real time using AWS Database Migration Service (DMS).
  2. Verification Phase: We run validation queries on the Green instance to ensure all data is consistent and accurate.
  3. Traffic Redirection: Once validated, we update route controls to safely point consumer-facing applications to the Green instance.
  4. Fallback Option: We keep the old Blue database online and synchronized for 48 hours, allowing us to roll back immediately if any unexpected issues occur.
