Section 1

1. Introduction

1.1 Purpose

This Functional Specification Document (FSD) defines the comprehensive behavior, data models, workflows, and user interface layouts for the Meeting Manager platform. It acts as the definitive baseline for software engineers, quality assurance testers, and project stakeholders to design, implement, and validate the system.

1.2 Scope

The Meeting Manager system encompasses end-to-end meeting lifecycle operations, including user authentication, meeting creation and scheduling, role assignments (hosts, participants), agenda management, real-time tracking, and administrative controls. Out-of-scope modules include custom telephony integrations and third-party accounting systems.

1.3 Objectives

  • Streamline corporate meeting scheduling and resource allocation.
  • Enforce structural agenda adherence and tracking.
  • Provide clear, role-based access control for administrative oversight.

1.4 Intended Audience

This document is intended for Product Owners, Software Developers, QA Engineers, Enterprise Architects, and Business Stakeholders.

Section 2

2. Business Context

Current Process (As-Is)

Meetings are currently scheduled via fragmented calendar tools with manual email threads for agendas, leading to unstructured discussions, missing notes, and zero systemic enforcement of meeting objectives.

Problems & Pain Points

  • Lack of centralized meeting agendas and structured tracking.
  • Confusion regarding roles (who is hosting vs. participating).
  • Time wastage due to unorganized discussion flows.

Future Process (To-Be)

A centralized platform enforcing strict scheduling parameters, structured agenda itemization, clear role assignments, and robust session management.

Business Benefits

  • Increased operational efficiency and shorter meeting durations.
  • Improved accountability through strict task and agenda tracking.
  • Standardized access management across organizational units.

Assumptions, Dependencies & Constraints

  • Assumptions: Users have modern web browsers with active internet connectivity.
  • Dependencies: Identity Provider (IdP) for Single Sign-On (SSO).
  • Constraints: System must comply with enterprise data retention policies.
Section 3

3. Functional Overview

The Meeting Manager system comprises the following primary modules:

  • Authentication & User Management: Role assignments, credential validation, and profile management.
  • Meeting Scheduling Module: Creation, updating, and cancellation of meetings, including date/time and agenda setup.
  • Participant Management: Adding, removing, and updating participant roles within a meeting.
  • Session & Dashboard Control: Real-time overview of active, upcoming, and past meetings.

Section 5

5. Functional Requirements

FR-001: Meeting Creation

Description: Allows authorized users (Hosts and Administrators) to schedule and create new meetings within the system.

  • Priority: Critical
  • Actor: Host, Administrator
  • Trigger: User clicks the "Create Meeting" button on the main dashboard.
  • Preconditions: User must be authenticated and possess Host or Administrator privileges.

Main Flow:

  1. User navigates to the Dashboard and selects "Create Meeting".
  2. System presents the Meeting Creation Form.
  3. User inputs meeting title, start date, end date, and description.
  4. User clicks "Save and Continue".
  5. System validates inputs against Business Rules (BR-001).
  6. System persists meeting record to database and displays success confirmation.

Alternative / Exception Flow:

If validation fails, system highlights invalid fields and prompts the user to correct errors without losing entered data.

Acceptance Criteria: System successfully creates a meeting record when all mandatory fields are provided with valid formats. Meeting appears immediately on the user's dashboard calendar view.

Business Rules: BR-001 | Related Screens: SCR-002 | Related APIs: POST /api/v1/meetings | DB Tables: meetings

FR-002: Add Meeting Agenda

Description: Enables hosts to append structured agenda items to an existing meeting.

  • Priority: High
  • Actor: Host, Administrator
  • Trigger: User selects an existing meeting and clicks "Add Agenda Item".
  • Preconditions: Meeting must be in "Scheduled" status.

Main Flow:

  1. User accesses meeting details view.
  2. User clicks "Add Agenda Item".
  3. User enters agenda title, description, and allocated duration in minutes.
  4. User clicks "Save Item".
  5. System validates duration against total meeting length (BR-002).
  6. System adds agenda item to the meeting agenda list.

Acceptance Criteria: Agenda items are cleanly displayed in sequential order with cumulative duration indicators.

Business Rules: BR-002 | Related Screens: SCR-003 | Related APIs: POST /api/v1/meetings/{id}/agenda | DB Tables: meeting_agendas

FR-003: Participant Management

Description: Allows hosts to add or remove participants from a scheduled meeting.

  • Priority: High
  • Actor: Host, Administrator
  • Trigger: User navigates to the "Participants" tab within meeting settings.
  • Preconditions: Meeting must exist and be editable.

Main Flow:

  1. User searches for user by email or name.
  2. User selects user from directory and clicks "Add to Meeting".
  3. System links user account as meeting participant.

Acceptance Criteria: Added participants immediately appear in the participant roster table.

Business Rules: BR-003 | Related Screens: SCR-004 | Related APIs: POST /api/v1/meetings/{id}/participants | DB Tables: meeting_participants

FR-004: Meeting Cancellation

Description: Allows hosts to cancel an upcoming meeting.

  • Priority: Medium
  • Actor: Host, Administrator
  • Trigger: User clicks "Cancel Meeting" action button.
  • Preconditions: Meeting status is "Scheduled".

Main Flow:

  1. User clicks "Cancel Meeting".
  2. System prompts for cancellation confirmation and optional reason.
  3. User confirms cancellation.
  4. System updates meeting status to "Cancelled".

Acceptance Criteria: Cancelled meetings are locked against further edits and updated across participant views.

Business Rules: BR-004 | Related Screens: SCR-002 | Related APIs: PATCH /api/v1/meetings/{id}/cancel | DB Tables: meetings
Section 6

6. Business Rules

Rule ID Title Description Enforcement Point Priority
BR-001 Future Meeting Scheduling Meeting start date and time must be set in the future relative to server time. Past dates are rejected. API / UI Validation Critical
BR-002 Agenda Duration Limit The sum of all agenda item durations cannot exceed the total scheduled duration of the meeting. API Service Layer High
BR-003 Host Modification Rights Only the designated meeting Host or an Administrator can modify meeting details or agenda items. Authorization Middleware Critical
BR-004 Cancellation Lock Once a meeting is marked as Cancelled or Completed, no further edits to agenda or participant lists are permitted. Database Constraint / Service Medium

7. UI Specification

SCR-002: Meeting Creation Screen

Purpose: Provides interface inputs for scheduling a new meeting.

Navigation Path: Dashboard > Click "Create Meeting"

Buttons / Actions: [Save and Continue], [Cancel]

Validation Rules: Title is required (max 150 chars). Start Date must be > current timestamp.

Responsive Behaviour: Form fields stack vertically on mobile screens and display in a two-column grid on desktop.

Accessibility Notes: All input fields feature explicit ARIA labels and keyboard tab navigation support.

Section 10

14. Non-Functional Requirements

  • Performance: API response times for meeting creation and retrieval must not exceed 500ms under normal load.
  • Availability: System uptime target of 99.9% during core business hours.
  • Security: All communication must be encrypted via TLS 1.3 in transit and AES-256 at rest. Role-based access enforced via JWT claims.
  • Browser Support: Fully compatible with the latest two stable versions of Chrome, Firefox, Safari, and Edge.
